## 0. Коротко: что строим

Свой мессенджер внутри кабинета RADI (тот же веб-кабинет, что открывается в Telegram и в мобильных
приложениях Android / iPhone). Менеджеры переписываются с клиентами **через кабинет**, а не в самом
Telegram: клиент видит обычные сообщения от рабочего Telegram-аккаунта компании, менеджер не имеет
доступа к самому аккаунту и **ничего не может удалить**. Рядом с перепиской — карточка клиента из BILLZ
(покупки, бонусы, долг, уровень, заметки). Руководитель видит все переписки всех менеджеров, скорость
ответа и сколько переписок закончились покупкой.

Основа уже есть: модуль `bizwatch.py` (контроль рабочих аккаунтов через Telegram Business) — он уже
получает и сохраняет все сообщения подключённых аккаунтов. CRM расширяет его: просмотр, ответы,
привязка к BILLZ, назначение менеджеров, отчёты.

## 1. О владельце и как с ним работать

- Владелец бизнеса XUPING / команда RADI (Узбекистан, бижутерия, опт и розница). Пишет по-русски,
  коротко, часто голосом/со скриншотами. Отвечать **по-русски**, коротко и по делу, без технических
  подробностей; шаги — нумерованным списком, что именно нажать.
- Сотрудники пользуются кабинетом на **узбекском или русском** (у каждого свой язык, `core.staff_lang`).
  Все тексты для сотрудников/менеджеров — на двух языках (ru/uz). Руководителю — по-русски.
- Владелец любит «элитный» вид: тёмно-фиолетовая тема RADI, логотип RADI & CO. по центру шапки.
- Владелец заранее разрешил: создавать PR и **сразу мержить** (squash) в `main` — Railway деплоит из `main`.
- Перед большой работой: задать уточняющие вопросы, дождаться «Да»/подтверждения ТЗ.
- После каждого шага — короткий отчёт: что сделано, как проверить, что ещё нужно от владельца.

### Правила безопасности (обязательно)
- Токены, ключи, пароли **никогда** не просить в чат и не класть в репозиторий. Только Railway → Variables
  (бот/сервер) или GitHub → Secrets (сборка iOS). Сказать владельцу, куда вставить, — самому не видеть.
- Ключ подписи Android (`*.keystore`) в репозиторий не коммитить (он в `.gitignore`).
- Личные данные клиентов — только на нашем сервере; во внешние сервисы не отправлять.
- Контроль переписок — **только рабочие аккаунты компании** и с ведома сотрудников. Тайное подключение к
  личным аккаунтам сотрудников не делать (обсуждалось и отклонено).

## 2. Проект: как устроен

Репозиторий `baleebaipro-jpg/staff-bot`, деплой — Railway (`python main.py`, `railway.json`).
Python 3, **python-telegram-bot 21.6**, Flask 3 + waitress, SQLite (`DATA_DIR/staff.db`).

| Файл | Что внутри |
|---|---|
| `main.py` | запуск: бот(ы) + веб-сервер кабинета |
| `bot.py` | Telegram-боты: сотрудников (`BOT_TOKEN`), клиентов (`CLIENT_BOT_TOKEN`), опционально контроля (`BIZ_BOT_TOKEN`); очередь `outbox_loop` (рассылает сообщения из таблицы `outbox`, раз в 1–10 с) |
| `webapp.py` | весь кабинет: Flask API `/api/*` + одна страница `PAGE` (HTML/CSS/JS в строке, ~3900 строк) |
| `core.py` | база, сотрудники, приход/уход, задачи, штрафы, клиенты бота, outbox, флаги |
| `erp.py` | интеграция BILLZ (клиенты, покупки, долги, бонусы, зеркало продаж) |
| `shop.py` | своя ERP-касса (этап 1): роли, точки, продажи, бонусы |
| `bizwatch.py` | **контроль рабочих аккаунтов (Telegram Business)** — база для CRM |
| `appauth.py` | вход в мобильные приложения через бот (токен сессии `appToken`) |
| `posts.py`, `projects.py`, `relay.py`, `invest.py` | постинг, проекты, пересылка фото фотографа, инвестиции |
| `i18n.py`, `staff_text.py` | тексты клиентов / сотрудников (ru, uz) |
| `config.py` | настройки: `ADMINS`, `EMPLOYEES` (id → имя, роль, график), каналы, флаги |
| `android/` | приложение Android (WebView на кабинет), `static/radi-team.apk` |
| `ios/` + `.github/workflows/ios-testflight.yml` | приложение iPhone (WKWebView), сборка в TestFlight |

### Важные механизмы
- **Авторизация в API**: декоратор `need_user(admin=False, staff=False)` в `webapp.py`. Тело запроса — JSON
  с `initData` (подпись Telegram WebApp) или `appToken` (мобильное приложение). `uid` передаётся в функцию.
  Руководитель — `core.is_admin(uid)`, сотрудник — `core.employee(uid)`.
- **Фронтенд**: функция `api(path, body)` → `fetch POST JSON`; `action(path, body)` — вызвать и перезагрузить
  данные (`load()`); экраны — `show(view)`, `SUBPAGES` (куда ведёт «Назад»), нижняя панель `tabbar`;
  листы-окна — `invSheet(html)` / `invSheetClose()`; тосты — `toast(msg)`; переводы сотрудника — `sx(key)`
  (словарь `SX.ru` / `SX.uz`). «Назад» в приложениях — `window.appBack()`.
- **Сообщения от бота**: не слать напрямую из Flask — класть в `outbox` (`core.notify(c, uid, text)`,
  колонки `photo` — путь к файлу / `tg:file_id` / `video:путь`, `markup`, `thread_id`, `via`).
- **BILLZ**: `erp.find_client(phone)`, `erp.customer_card(billz_id)` (статистика, заметки, история покупок),
  `core.billz_base(...)` (единый список клиентов бот+BILLZ), таблицы `billz_clients`, `billz_sales`.
  Фоновый поток `erp.start_purchase_watch` раз в 30 с видит новые покупки — можно использовать для
  отметки «🛍 Покупка» в чате.
- **Тема/вид**: CSS-переменные в `PAGE` (`--card`, `--line`, `--muted`, `--hint`, `--red`, `--green`…),
  классы `.card`, `.btn btn-main / btn-soft / btn-sm`, `.empty`, `.hint`, `.f-ic`. Логотип `/static/radi-logo.png`.

### Как разрабатывать (принятый порядок)
1. Ветка разработки, коммит с подписью (см. системные инструкции сессии).
2. Проверка: `python3 -m py_compile ...`, затем **Playwright** против локального сервера с подставным
   Telegram (`window.Telegram.WebApp` подменяется через `page.route('https://telegram.org/**')`), подписанный
   `initData` для руководителя и сотрудника. Скриншоты смотреть самому.
3. BILLZ в тестах — подставной HTTP-сервер (реальный BILLZ из среды разработки недоступен).
4. Telegram-обновления — имитировать через `Update.de_json(dict, Bot("123456:TEST"))` и фальшивый `bot`
   с записью вызовов (так тестировался `bizwatch`).
5. PR → squash-merge в `main` → ветку сбросить на `origin/main`.
6. Railway-хост из среды разработки недоступен — работу в проде проверяет владелец по шагам.

  file_id, sent_at, edited, deleted_at)`, `biz_events(conn_id, chat_id, chat_name, kind, info, at)`.

- Уведомления руководителю: подключение/отключение бота, ✏️ изменение (было/стало), 🗑 удаление (текст,
  медиа пересылаются, длинная переписка — файлом). Команда `/biz` — диагностика.
- **Критично**: в PTB 21 `effective_message` и `MessageHandler` ловят и `business_message`. Поэтому
  `bizwatch.on_update` стоит `TypeHandler` в группе **-100** и после обработки бросает
  `ApplicationHandlerStop` — иначе обычные обработчики бота начнут отвечать клиентам в чужих чатах.
  Не ломать это при доработке.

### Проверено владельцем на живом аккаунте
- Удаление отдельного сообщения (и «у себя», и «у всех») — приходит.
- Изменение — приходит.
- **Удаление чата целиком — Telegram боту НЕ присылает** (ограничение Bot API). Поэтому ценность —
  в полном архиве: всё, что прошло после подключения, хранится у нас, даже если чат удалён.
- Сообщения до подключения боту неизвестны («текст неизвестен»).

## 4. Ограничения Telegram (учесть в дизайне)

**Способ 1 — Telegram Business бот (официальный, выбран по умолчанию):**
- Бот получает все личные (1-на-1) сообщения аккаунта после подключения, исходящие тоже.
- Отправка от имени аккаунта: `bot.send_message(chat_id, text, business_connection_id=...)`
  (и `send_photo`, `send_video`, `send_voice`, `send_document`… с тем же параметром).
  Требует права «Ответы на сообщения» у подключения.
- **Окно 24 часа**: бот может отвечать только в чатах, где была активность за последние 24 часа
  (так написано в настройках Telegram у владельца). Первым написать «давнему» клиенту нельзя —
  только вручную из Telegram. В интерфейсе показывать: «⏳ Окно ответа закрыто — клиент писал N ч назад».
- Нет истории до подключения, нет списка чатов аккаунта, нет события «чат удалён целиком».
- Группы, каналы, секретные чаты — недоступны.
- Новые методы Bot API (отметка «прочитано» — `readBusinessMessage`, права `BusinessBotRights` вместо
  `can_reply`) есть в новых версиях Bot API / PTB 22.x. Сейчас стоит **PTB 21.6** — при необходимости
  обновить с проверкой всего бота (см. этап 5).

**Способ 2 — вход в аккаунт с сервера (MTProto, как Novagram / Telethon):**
- Без окна 24 часа, можно писать первым, вся история, видно удаление чатов.
- Риски: блокировка аккаунта Telegram за работу с сервера, полный доступ к аккаунту хранится на сервере
  (утечка = угон аккаунта). Нужны `api_id/api_hash` с my.telegram.org и вход по коду.
- Делать **только по явному решению владельца**, только для рабочих номеров, сессию хранить
  зашифрованной (ключ — в Railway Variables). Это отдельный этап (6), не начинать по умолчанию.

## 4а. Как проходит сделка (утверждено владельцем — делать именно так)

Менеджер работает **только в CRM** (вкладка «Чаты» в кабинете RADI: телефон или компьютер).
Клиент остаётся в обычном Telegram и получает ответы от рабочего аккаунта компании — он не знает,
что менеджер отвечает из CRM.

1. **Клиент пишет** в Telegram на рабочий аккаунт (например @xupingleader) → через 1–2 с сообщение
   появляется в CRM в списке чатов с меткой «🆕 новый». Менеджеру — уведомление в бот:
   «Новое сообщение от Малика З.» (на языке менеджера).
2. **CRM узнаёт клиента**:
   - есть в BILLZ (по номеру / имени / ранее привязан) → справа карточка: уровень, сумма покупок,
     бонусы, долг, последняя покупка, заметки;
   - нет → «новый клиент»; менеджер просит номер — CRM находит клиента в BILLZ или готовит к заведению.
3. **Менеджер ведёт переписку из CRM**: текст, фото/видео товара, голосовые; быстрые ответы ⚡ (прайс,
   адрес, реквизиты, график); статус сделки **новый → в работе → ждём оплату → купил / отказ**
   (отказ — с причиной); заметки к клиенту («хочет серьги под золото, бюджет 300 тыс.»).
4. **Оплата и покупка**: продажа проводится в **BILLZ** как обычно → CRM видит новую покупку этого
   клиента (≤ 30 с, через `erp.start_purchase_watch` / `billz_sales`) → в чате появляется
   «🛍 Покупка 450 000 сум · 24.11» → сделка автоматически закрывается статусом «купил» и
   **засчитывается менеджеру**, который вёл переписку.
5. **После покупки**: клиенту в клиентский бот — «спасибо» и новые бонусы (как сейчас);
   менеджер может поставить напоминание «написать через 2 недели» (напоминание приходит менеджеру в бот;
   написать первым из CRM — только при открытом окне 24 ч, иначе вручную из Telegram).

**Руководитель видит**:
- все чаты всех менеджеров, включая удалённые и изменённые сообщения;
- скорость ответа (кто отвечает за 2 мин, кто за час; сколько чатов без ответа);
- воронку по менеджерам: «Moxira: 40 чатов → 12 покупок → 8 400 000 сум»;
- контроль: менеджер не знает пароль рабочего аккаунта и ничего не может удалить
  (удалить может только клиент у себя — копия у нас остаётся; при ответах только через CRM
  «кто удалил» становится однозначным — менеджер удалить не может).

**Ограничение (способ 1)**: ответ из CRM — только если клиент писал последние 24 часа; написать
первым «молчащему» клиенту — из самого Telegram (телефон руководителя/старшего). Если это нужно
постоянно — способ 2 (MTProto), только по решению владельца (см. раздел 4).

**Что нужно для запуска**: рабочие аккаунты Telegram с Premium (@xupingleader уже подключён);
у подключения бота включить право «Ответы на сообщения»; доступ менеджерам к CRM — в их карточке
(как сейчас «Продажи»).

## 5. Техническое задание CRM

### 5.1 Роли и доступ
- **Руководитель** (`ADMINS`): все аккаунты, все чаты, назначение менеджеров, отчёты, архив удалённого.
- **Менеджер** (сотрудник с правом CRM): видит чаты своих рабочих аккаунтов (или назначенные ему),
  отвечает, ставит статусы, пишет заметки. Не видит отчёты по другим менеджерам.
- Право CRM выдаёт руководитель в карточке сотрудника (по аналогии с правом «Продажи»/«Постинг»).
- Привязка «рабочий аккаунт → менеджеры» (один аккаунт могут вести несколько менеджеров по сменам).

### 5.2 Экран «Чаты» (новая вкладка кабинета)
- Список чатов: аватар/инициалы, имя клиента (из BILLZ, если найден, иначе из Telegram), последнее
  сообщение, время, счётчик непрочитанных, метка статуса, значок «окно 24 ч закрыто».
- Фильтры: все / мои / непрочитанные / без ответа > 15 мин / по статусу / по аккаунту.
- Поиск: имя, телефон, @username, текст сообщений.
- Обновление: опрос API раз в 3–5 с, пока открыт экран (WebSocket не нужен на первом этапе).

### 5.3 Экран переписки
- Лента сообщений как в Telegram: входящие слева, исходящие справа; время; медиа (фото, видео, голосовые,
  файлы — отдаём через наш прокси по `file_id`, см. 5.6); ✏️ «изменено» (по нажатию — старый текст);
  🗑 удалённые — видны руководителю (красным), менеджеру — нет или серым (уточнить).
- Поле ввода + отправка текста; прикрепить фото/файл; быстрые ответы-шаблоны (кнопка ⚡).
- Если окно 24 ч закрыто — поле ввода заблокировано с пояснением.
- Сообщения, отправленные менеджером из кабинета, помечаются, **кто** отправил (в Telegram клиенту —
  от аккаунта компании; у нас — «Moxira»). Сообщения, написанные из самого Telegram (не через CRM), —
  «📱 из Telegram».
- «🛍 Покупка 450 000 сум · 24.11» — системные отметки в ленте, когда у привязанного клиента появилась
  покупка в BILLZ (из `erp.start_purchase_watch` / `billz_sales`).

### 5.4 Карточка клиента (справа / по кнопке на телефоне)
- Привязка к BILLZ: автоматически по телефону (если клиент поделился контактом / номер в Telegram известен)
  или вручную — поиск по BILLZ (`shop.search_clients` / `core.billz_base`), кнопка «Привязать».
- Данные: имя, телефон, уровень (Bronza/Silver/Gold — `core.CLIENT_TIERS`), покупки (сумма, число, последняя),
  бонусы, долг (`erp.debts`), заметки BILLZ + свои заметки CRM, история покупок (`erp.customer_card`).
- Кнопка «Открыть полную карточку» → существующий экран `view-ccard`.
- Статус лида: новый / в работе / ждём оплату / купил / отказ (+ причина). Ответственный менеджер.

### 5.5 Отчёты для руководителя
- По менеджерам: чатов, сообщений, среднее время первого ответа, без ответа > N мин.
- Конверсия: переписок → покупок в BILLZ за 7/30 дней после последнего сообщения, сумма продаж.
- Архив: удалённые сообщения (уже есть в `biz_messages.deleted_at`), изменённые, события отключения бота.

### 5.6 Сервер (API, черновик)
- `POST /api/crm/chats` {filter, q, account} → список чатов (из `biz_messages` + новая таблица `crm_chats`).
- `POST /api/crm/messages` {conn_id, chat_id, before?} → лента (пагинация по 50).
- `POST /api/crm/send` {conn_id, chat_id, text | file(base64)} → отправка через бота с
  `business_connection_id`; запись в `biz_messages` (outgoing=1, `sent_by` = uid менеджера).
  Отправку делать **через очередь** (новый тип записи в `outbox` или отдельная таблица `crm_outbox`,
  которую разбирает `outbox_loop` ботом, к которому подключён аккаунт), ответ API — «отправляется»;
  статус (отправлено/ошибка, напр. «окно 24 ч закрыто») — в ленте.
- `POST /api/crm/read` {conn_id, chat_id} → отметить прочитанным у нас (и, если появится в PTB, в Telegram).
- `POST /api/crm/link` {conn_id, chat_id, billz_id} → привязка к клиенту BILLZ.
- `POST /api/crm/status`, `/api/crm/note`, `/api/crm/assign`, `/api/crm/templates`, `/api/crm/report`.
- `GET /crm/media/<conn>/<chat>/<msg>` → скачать файл через `bot.get_file(file_id)` и отдать (с кэшем на диске
  `DATA_DIR/crm_media`, срок как у переписки). Доступ — только авторизованным (токен в query/cookie).

### 5.7 База (черновик, добавить к таблицам `bizwatch`)
- `biz_messages` + колонки: `sent_by INTEGER` (кто из менеджеров отправил из CRM), `read_at TEXT`,
  `status TEXT` (для исходящих из CRM: queued/sent/failed), `error TEXT`.
- `crm_chats(conn_id, chat_id, billz_id, phone, status, reason, manager_id, last_in_at, last_out_at,
  unread INTEGER, first_reply_sec, updated_at, PRIMARY KEY(conn_id, chat_id))`.
- `crm_notes(id, conn_id, chat_id, uid, text, at)`, `crm_templates(id, title, text, lang, sort)`.
- `crm_access(uid PRIMARY KEY, role, accounts TEXT)` — кто менеджер и какие аккаунты ведёт.
